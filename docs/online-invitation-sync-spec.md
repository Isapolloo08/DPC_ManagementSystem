# Online-to-Local Invitation Submission Notification and Manual Pull Synchronization

Specification synthesized from confirmed interview decisions Q1-Q17 and ADR-0001. The user confirmed both testing boundaries and authorized GitHub publication on October 11, 2026. This document authorizes neither implementation nor deployment by itself.

Published specification: [GitHub issue #1](https://github.com/Isapolloo08/DPC_ManagementSystem/issues/1), labeled `ready-for-agent`. Publication completed on October 11, 2026.

## Problem Statement

People can submit event invitation responses through the public invitation website while DPC staff operate a separate Local Master database. An Admin using the local application cannot currently discover and selectively import those online responses through an in-app pending-submission workflow. The existing broad Cloud Sync transfers many unrelated records and has no per-submission revision receipt or online confirmation, so it cannot serve as the invitation-specific Pull action safely.

Administrators need to know that responses are waiting, inspect them, and deliberately import selected responses without exposing localhost publicly, automatically importing business data, overwriting newer online answers, duplicating records, or changing actual attendance. Responses must remain available while the Local Master is offline, and uncertainty after an interrupted request must not cause duplicate imports or incorrect synchronization status.

## Solution

Pair the Local Master once with the verified online backend through an authorized cloud Admin. While the Master is running and a valid local Admin session is active, it checks online availability over outbound HTTPS approximately every 30 seconds and on startup/reconnection after readiness. Automatic checks obtain only minimal availability metadata.

Group alerts by event in the existing notification bell. An alert opens the corresponding event invitation modal, which shows pending items, connection freshness, and individual or selected Pull actions. An Admin can request a transient online preview. Checking, previewing, reading an alert, and dismissing an alert never import a response into local business records.

Explicit Pull fetches the latest available submission revision, validates it and its verified parent identities, and commits the response, applicable planned member registration, and durable import receipt together in one local transaction per submission. Actual attendance and attended/checked_in registration status are preserved. Only after that commit does the Master confirm the exact imported revision online.

If import fails, the item remains pending or blocked with a useful reason. If import succeeds but confirmation fails, show Imported locally / Confirmation pending and automatically retry confirmation only. New online revisions require another explicit Pull. LAN clients share the Master's synchronization state. Backup/restore reconciliation compares retained online revisions with actual local receipts rather than relying on previous cloud confirmations alone.

## User Stories

1. As an invitation recipient, I want to open a publicly accessible invitation link, so that I can respond without a staff account or access to the local network.
2. As an invitation recipient, I want my accepted response stored online while the Local Master is offline, so that my answer is available when staff reconnect.
3. As a regular member, I want my invitation response associated with my verified existing member and event counterparts during import, so that staff see the correct planned registration.
4. As a guest, I want my invitation response preserved as a guest response, so that responding does not create a membership or account for me.
5. As an invitation recipient, I want to change my answer while the invitation accepts responses, so that staff can manually retrieve my latest intention.
6. As an event organizer, I want existing link types, ministry scope, public validation, deadlines and deactivation to continue working, so that this feature preserves the invitation workflow.
7. As a cloud Admin, I want to pair the Local Master with the intended online service, so that response data comes from the correct source.
8. As a cloud Admin, I want a revocable integration credential scoped to invitation synchronization, so that local synchronization does not require broad online database access.
9. As a local Admin, I want the cloud pairing to persist across ordinary local sessions, so that I do not need to log into the cloud account on every use.
10. As a local Admin, I want clear Reconnect required feedback when pairing is revoked or unusable, so that I know how to restore access.
11. As a local Admin, I want a backend/database identity mismatch to block synchronization, so that the application cannot silently connect me to the wrong church data source.
12. As a local Admin, I want automatic availability checks while my authorized session is active, so that I learn about pending responses without manually refreshing all events.
13. As a local Admin, I want availability checked on startup and reconnection after readiness, so that submissions accepted during downtime become visible.
14. As a local Admin, I want checks to continue while the application is minimized or in the tray, so that I can receive updates during normal desktop use.
15. As a local Admin, I want discovery and Pull paused when no valid Admin session is active, so that expired or logged-out sessions cannot retrieve response data.
16. As a LAN Admin, I want clients connected to the same Local Master to share pending and imported status, so that different computers see one receiving database's synchronization history.
17. As a local Admin, I want grouped event alerts in the existing notification bell, so that pending submissions are noticeable without adding dashboard clutter.
18. As a local Admin, I want an alert to open the relevant event invitation modal, so that I can act on the correct event directly.
19. As a local Admin, I want pending-import count separate from unread-alert count, so that reading a notification does not hide unfinished synchronization.
20. As a local Admin, I want genuinely new or changed submissions to generate an updated alert, so that I can distinguish new work from repeated checks of the same work.
21. As a local Admin, I want polling to persist only minimal availability metadata, so that sensitive response data is not imported or cached automatically.
22. As a local Admin, I want to request a response preview containing its name, contact, answer and reason, so that I can review it before deciding to Pull.
23. As a local Admin, I want preview data cleared on logout, so that another session cannot see my transient response details.
24. As a local Admin, I want an explicit Pull button for one submission, so that I control precisely which response enters the local database.
25. As a local Admin, I want Pull Selected within an event, so that I can import a chosen set without pulling every pending response.
26. As a local Admin, I want each selected response to produce its own success or failure result, so that one invalid item does not roll back other successfully imported items.
27. As a local Admin, I want repeat clicks and retries to avoid duplicate imports, so that uncertain outcomes do not create duplicate responses or registrations.
28. As a local Admin, I want the response and its planned registration saved with the import receipt in one transaction, so that a submission cannot appear imported after only part of its required local data was saved.
29. As a local Admin, I want missing or ambiguous local event/member/invitation counterparts to block the item, so that synchronization cannot associate a response with the wrong person or event.
30. As a local Admin, I want a clear blocked-item explanation, so that I can arrange an explicit dependency repair instead of relying on automatic parent creation.
31. As a local Admin, I want the latest available online answer applied at Pull, so that the local invitation response reflects the recipient's current intention.
32. As a local Admin, I want a newer answer arriving during Pull to remain pending, so that importing an older revision cannot conceal a subsequent change.
33. As a local Admin, I want online invitation answers to control the local invitation response after Pull, so that stale local response values do not supersede the online source.
34. As an attendance operator, I want invitation synchronization to preserve actual attendance and attended/checked_in registration status, so that an RSVP change cannot undo a confirmed arrival.
35. As a local Admin, I want online confirmation to follow the local commit, so that an unsuccessful import cannot be marked synchronized.
36. As a local Admin, I want a confirmation failure displayed as Imported locally / Confirmation pending, so that I understand the local response is already saved.
37. As a local Admin, I want confirmation retried after failure or restart without re-importing, so that temporary online failures recover without duplicate business writes.
38. As a local Admin, I want acknowledgement of an older revision to leave a newer revision pending, so that confirmation cannot lose a changed answer.
39. As a local Admin, I want interrupted requests and unknown commit outcomes reconciled from durable state, so that the application reports what actually happened rather than assuming success or failure.
40. As a local Admin, I want last-known pending information and the last successful check shown while offline, so that unavailable online data is not mistaken for zero pending submissions.
41. As a local Admin, I want bounded retries and quiet retry/offline states, so that network failures do not flood notifications or overload the online service.
42. As a local Admin, I want previously accepted responses pullable after the deadline, event start or link deactivation, so that a delayed manual synchronization does not lose valid responses.
43. As a cloud Admin, I want destructive deletion blocked when it would remove unimported responses, so that submissions retained for an offline receiver are protected.
44. As a local Admin, I want notification cleanup and dismissal to leave pending submissions intact, so that alert lifecycle does not control response retention.
45. As a backup operator, I want receiver identity, mappings and import receipts included in compatible local backups and restores, so that synchronization can recover its history safely.
46. As a local Admin restoring older data, I want retained online revisions compared against restored local receipts even when already acknowledged online, so that missing local responses become pending for manual Pull again.
47. As a local Admin restoring data, I want unresolved identity mappings reported as blockers, so that recovery does not guess identities or silently duplicate records.
48. As a local Admin, I want broad Cloud Sync to preserve newer online-owned answers and the dedicated Pull boundary, so that its existing Push/Pull operations cannot bypass this workflow.
49. As an event organizer, I want existing invitation publication and other supported cloud transfers preserved, so that protecting invitation answers does not disable unrelated work.
50. As a non-Admin user, I want the application's existing permissions respected, so that this feature does not grant me access to pending online responses or Pull actions.
51. As a local Admin, I want pending items and status controls to follow DPC's existing light/dark, responsive and accessible UI patterns, so that the workflow remains usable and visually consistent.
52. As a local Admin, I want a record of explicit Pull outcomes associated with the acting user, so that synchronization actions can be explained using the existing audit architecture.

## Implementation Decisions

- **Architecture and ownership:** Extend the existing Express backend and PostgreSQL model. Use one receiving Local Master with shared LAN clients. Use the existing Render service as the online API and its verified durable database as the source. No inbound public route to localhost is required.
- **Transport:** The Master initiates outbound HTTPS metadata requests approximately every 30 seconds while at least one valid authorized local Admin session is active. Check promptly after startup/reconnection once schema and pairing readiness are established. Use one non-overlapping backend scheduler rather than one poller per browser. Use bounded requests, backoff/jitter, rate-limit-aware retries and explicit freshness state. The interval is a healthy-state scheduling target, not an outage-time delivery SLA.
- **Reuse local delivery:** Reuse authenticated local Socket.IO user delivery and existing notification storage/dispatch patterns. Limit this feature's notifications and state access to Admin, matching existing Cloud Sync role compatibility. Current Pastor/Coordinator invitation management access is preserved; it does not grant access to this synchronization feature.
- **Session lifecycle:** Re-check authorization server-side for metadata, preview and Pull. Expired/revoked local authority stops new discovery/import work; minimized/tray operation continues with a valid session. Clear transient previews and cancel further preview requests on logout. No checks run when the Master/backend is closed. Previously committed receipt-based confirmations may retry independently without fetching/importing payloads.
- **Pairing:** An authorized cloud Admin explicitly pairs the receiver with the verified source once. The pairing issues a narrowly scoped, revocable integration credential for that source/receiver, kept in protected local backend storage. Do not persist cloud account passwords for this integration or expose integration/database credentials in renderer configuration, notifications, previews, logs or frontend builds. Reuse existing authentication/role validation; a local JWT is not a cloud identity.
- **Source verification:** Establish source/receiver identity before discovery or Pull. Verify the Render backend's database correspondence instead of assuming root development settings or existing Cloud Sync settings identify the same source. A mismatch blocks integration with a useful explanation and does not silently change existing database configuration. Credential revocation/unusable pairing produces Reconnect required rather than empty pending results.
- **Existing online submission behavior:** Keep public invitation token validation, member/guest inputs, event/ministry scope, public response deadlines, rate limiting and transactional RSVP writes. Record revision identity as part of successful source response persistence; rejected submissions do not become pending. Public pages receive no staff synchronization privileges.
- **Durable identity/revisions:** Add additive schema state for stable source/receiver identity, distinguishable submission revisions, verified parent mappings, per-revision local import receipts and durable pending confirmations. Source identities remain stable across repeat responses and receiver identities survive compatible backups. Prefer existing proven link/response uniqueness where it is sufficient; integers shared by two databases or names alone are not evidence of parent identity. Neither count differences nor last-sync timestamps define pending work.
- **Metadata contract:** Authenticated availability reads return only opaque submission identity/revision, the authorized event reference/title, counts and update time needed for pending discovery. Use bounded/paginated results and completeness/freshness information so a truncated result cannot be treated as the whole pending set. Exclude respondent names, contacts, answers, reasons and invitation bearer tokens from automatic discovery. Cached metadata is not an imported invitation response.
- **Preview contract:** An authorized explicit preview obtains the current online response details transiently. It creates neither local response/registration writes nor an import receipt/confirmation. It does not reserve a response revision. Names, contacts, answers and reasons are not persisted locally before Pull; render them safely as data and clear them when authorization ends.
- **Pending reconciliation:** Determine pending status by current source revisions relative to actual local import receipts, scoped to this receiver. A newer online revision is pending again. Remote confirmations cannot by themselves hide a revision missing from restored local state. Locally imported revisions awaiting confirmation are shown separately rather than offered as unimported work merely because the server has not recorded confirmation yet.
- **Notifications:** Deduplicate repeated discovery of the same source revision/recipient and group alerts by event. Update availability for genuinely new/changed revisions without repeated toasts for unchanged polls. Notification read/dismiss status and pending-import status are separate. Notification expiry/cleanup does not remove submission state. Reconcile availability when opening the bell/event panel when authorized and reachable; offline displays remain explicitly stale.
- **Navigation/UI:** Extend the existing bell and event invitation modal, including event-specific navigation, a pending-online section, optional preview, Pull and Pull Selected controls, per-item busy/error results and freshness/status indicators. Reuse existing modal, button, badge, toast and semantic design patterns, including navy/gold identity, light/dark modes and responsive behavior. Do not add a new dashboard widget. Differentiate unanswered invitations from submitted responses pending import.
- **Explicit Pull contract:** A local Admin selects one item or a bounded set within an event and deliberately starts Pull. The backend fetches the latest available revision for each selected source identity, validates the source and the full response, verifies parent counterparts and permissions, and reports the revision actually committed. Fetching a newer answer after preview is allowed; a source change later than the fetched revision remains pending. Automatic discovery/recovery never starts a response import.
- **Validation and mapping:** Validate supported answer values, required decline reason, field types/limits, source identity/revision, event/member/invitation correspondence, and appropriate member/guest relationships before committing. Preserve retrieval of already accepted responses after public closure. Missing source data, schema incompatibility, unavailable dependencies and ambiguous mappings block the item with an actionable result. Do not silently create members/events, infer from matching numeric IDs, or skip failures as successes.
- **Local atomicity:** Commit the response, its applicable planned member registration, verified mapping state needed for that import, and a receipt/pending-confirmation record in one local transaction per item. Failure before commit rolls back the item's writes. Never mark synchronized before local commit. Do not hold a local import transaction open while waiting for remote confirmation.
- **Idempotency and concurrency:** Enforce durable source/receiver/revision uniqueness and prevent concurrent import of the same logical response from creating duplicates or downgrading a newer local imported revision. Honor existing per-event/member response and registration uniqueness, including member answers across invitation links. Repeat clicks, overlapping Admin requests, lost HTTP replies and retry after restart reconcile committed receipts and business state rather than repeat the import. Repeated request identity must not be the only protection.
- **Response authority:** Online answers own the imported invitation response. Member answers update only planned registrations: Attending -> registered, Cannot attend -> cancelled, Not yet sure -> pending, while preserving attended/checked_in status. Actual attendance records are untouched. Guest responses remain guest responses and do not create members, member registrations or staff accounts.
- **Batch behavior:** Individual Pull and Pull Selected are supported within an event. Each selected response has its own transaction and outcome. Return individual committed/confirmation-pending/already-imported/failed/blocked results; successful items remain committed when another fails. Failed or unprocessed items stay available for another explicit Pull. Bound batch size and execution time; cancellation does not erase prior item commits.
- **Confirmation contract:** Confirm only an exact locally committed source revision for the paired receiver. Confirmation is idempotent, scoped and durable; confirming an old revision cannot clear a newer one or change the online answer. Mark fully synchronized after local commit and successful online confirmation. The state Imported locally / Confirmation pending means no further local import is needed for that revision.
- **Recovery:** Persist pending confirmation with the local transaction. Retry confirmation automatically with backoff after remote/network failure and after restart, including unknown remote-confirmation outcomes. Retry only committed receipt-based confirmations; never fetch/import a newer answer as part of recovery. If the local commit outcome was unknown to the client, re-read durable state before another attempted import. Report recoverable connectivity problems separately from validation/identity blocks.
- **Offline behavior:** Keep online accepted submissions durable independently of the Master's availability. Retain last-known minimal metadata and last successful check locally, showing stale/offline/retrying explicitly. Neither disconnect nor a server/auth error sets pending count to zero or produces a successful synchronization result. Resume discovery after authorized reconnection/readiness.
- **Retention:** Previously accepted responses remain eligible for Pull after deadline, event start and link deactivation. Pending responses have no automatic expiry. Guard destructive event/link and other cascading deletion paths that would remove unimported source responses. Preserve deactivation/closure as safe ways to stop new responses. The initial version introduces no new Reject/Archive operation. Notification cleanup never serves as a response-retention policy.
- **Backup/restore:** Include compatible receiver identity, mappings, receipt and pending-confirmation state in backups/restores with referentially correct ordering. Restore reconciles actual local receipts with retained current source revisions even if the cloud previously confirmed them. Missing local versions become pending and need explicit Pull. Lost/ambiguous mapping or source identity is a blocker. Never duplicate/import automatically as a side effect of restore. Already deliberately deleted remote records require a valid backup; confirmations alone cannot recover their payloads.
- **Broad Cloud Sync interaction:** Keep other supported records and invitation publication working while preventing general Pull from importing pending online responses around dedicated Pull approval. Prevent stale Push from overwriting newer online-owned responses or invitation-controlled planned-registration fields. Preserve actual attendance and existing parent/link publication. Do not blindly remove the entire registration table from transfer; protect the relevant ownership/field boundary consistently. Exclude receiver-local credentials and import/confirmation history from generic cross-environment overwrites. If the safety boundary or provenance cannot be verified, fail the conflicting transfer safely rather than reverting to broad overwrite behavior.
- **Audit and errors:** Reuse existing audit attribution for deliberate Pull and batch outcomes without logging bearer tokens, credentials or sensitive full payloads. Provide useful validation/mapping and connection/auth errors; distinguish failed local import from failed online confirmation. Expose resulting state through the existing local API/notification patterns.
- **Compatibility/readiness:** Use additive, repeatable migrations and verify required schema capabilities before declaring the synchronization feature ready. Existing health success alone is insufficient proof. Backfill preexisting submission identity/revision state safely without inventing parent correspondence; block unsupported legacy mappings for explicit repair. Implement no general renumbering, destructive reconciliation or unrelated auth/database redesign.
- **Dependencies/deployment:** Reuse existing HTTP, PostgreSQL, authentication and Socket.IO capabilities. No additional backend, Redis, message broker, cloud-to-local webhook, SSE service or mandatory second WebSocket connection is needed. A completed implementation will require separately authorized local/online rollout; the current specification workflow changes no running service or database.

## Testing Decisions

The user confirmed the following two testing boundaries. Tests assert externally observable behavior and durable outcomes, not private helper calls, polling implementation structure, exact SQL text or incidental component markup.

1. **Primary boundary: authenticated Express API and persisted outcomes across isolated online/local PostgreSQL environments.** Reuse the existing invitation HTTP/PostgreSQL integration approach and cloud-transfer isolation patterns. Run actual public submission and authorized synchronization operations through in-process test HTTP servers backed by disposable test databases/schemas. Control transport failures, response races, time and restart lifecycle without writing to configured production/cloud or the real local business schema. Assert public API results and relevant persisted outcomes. The remote HTTP dependency may be controlled for network faults; atomicity, uniqueness and revision behavior must use real PostgreSQL rather than mocked database success.
2. **Supporting boundary: the Admin browser journey.** Extend existing Playwright invitation/notification fixtures to exercise bell -> correct event -> pending section -> transient preview -> explicit Pull, including no business write before Pull, selection/partial failure, confirmation-pending status, unread-versus-pending distinction, stale/offline feedback, logout clearing and role visibility. Cover light/dark and narrow desktop/mobile layouts using existing UI verification patterns. Fixtures verify UI behavior; they do not replace database integration evidence.

Required API/persistence scenarios:

- Accepted member/guest submissions are durable online and discovery leaves local response/registration state unchanged.
- Public rejection/deadline/ministry/decline-reason behavior remains intact; existing valid general/personal links continue working.
- Pairing and every metadata/preview/Pull/confirmation operation reject unauthorized, expired, revoked, wrong-source and wrong-receiver access. A local JWT alone cannot impersonate a cloud user. Responses/logs contain no integration secrets; automatic metadata omits sensitive fields and invitation tokens.
- Discovery catches already-pending and updated revisions, handles pagination, reconnect and duplicate polls, and never mistakes errors/partial results for an empty inbox. Multiple LAN clients do not create independent receivers or duplicate polling/import history.
- Explicit member Pull atomically saves the response, appropriate planned registration and receipt; explicit guest Pull saves only the guest response and receipt. Attended/checked_in status and actual attendance remain unchanged.
- Inject a failure during each item's local writes and verify no partial response/registration/receipt/confirmation claim is committed.
- Repeated clicks, parallel Pulls, repeat responses across member links, and unknown commit outcomes do not duplicate or regress imported data. Separate source guest records remain separate; do not merge people heuristically by name/contact.
- A source answer changed after preview is fetched as the latest available revision at Pull; changes arriving after the fetched revision remain pending. A delayed older local import or acknowledgement cannot overwrite/hide newer imported/source revisions.
- Missing or conflicting parents, schema drift, mismatched source pairing and source deletion produce blocked results without automatic dependency creation or association by numeric ID alone.
- Selected batches report per-item outcomes, preserve successful item commits despite another item's failure, and leave unprocessed/failed items pending under interruption.
- Failed remote confirmation after local commit exposes Confirmation pending. Simulated process restart and repeat acknowledgement recover without another import; a newer source answer still requires explicit Pull.
- Deadline/event-start/deactivation changes prevent new public submissions as appropriate but do not prevent pulling previously accepted responses. Cascading deletion is blocked while it would erase unimported submissions.
- Real broad Push/Pull compatibility checks preserve newer online-owned responses and invitation-controlled registration fields, prevent approval bypass, retain other supported transfers and keep actual attendance safe.
- Compatible backup/restore preserves receiver identity/mappings/receipts and pending confirmations. Restoring older receipts rediscovers retained missing revisions despite earlier online confirmations; restore itself performs no business import. Missing mappings fail safely.
- Controlled clock/lifecycle tests verify approximately 30-second healthy polling, one in-flight check, backoff/rate-limit handling, readiness gating, active authorization, tray operation, logout pause and acknowledgement-only recovery.

Prior art consists of the existing invitation permission/public-response tests, isolated PostgreSQL invitation/member RSVP tests, PostgreSQL cloud-transfer retry/identity/rollback/cancellation tests, and Playwright invitation, notification-design and backup-management journeys. Extend the highest public boundaries available rather than adding a unit-test seam for each internal function.

Before implementation is declared complete, require relevant frontend/backend typechecks/build checks, focused API/PostgreSQL and browser suites, and existing invitation/cloud-sync/backup regressions affected by the change. Report skipped/unavailable real-database checks as gaps rather than passes. No new tests or implementation are executed by this specification workflow.

## Out of Scope

- Automatic importing of invitation responses, including import triggered by polling, preview, notification reading/dismissal, restore or newer-answer recovery.
- Exposing localhost publicly, inbound online-to-local webhooks, a separate cloud backend, Redis/message brokers, new SSE infrastructure or a mandatory cloud WebSocket connection.
- Multiple independent receiving local databases or multi-church/tenant synchronization.
- Full answer-edit history, new Reject/Archive controls, automatic guest-to-member/account creation, or new identity verification for public invitation recipients.
- Creating/importing missing members/events automatically, guessing existing counterpart identity from names or numeric IDs, general ID renumbering, or a new general-purpose manual-repair interface.
- Replacing the existing DPC design system, adding a dashboard widget, broadening Pastor/Coordinator feature permissions, or redesigning unrelated notifications/authentication.
- Converting planned RSVP into actual attendance, undoing confirmed check-in, or changing unrelated church workflows.
- A blanket full-database synchronization redesign beyond changes necessary to preserve invitation ownership, safe publication and manual-import approval.
- A guaranteed 30-second detection SLA during offline periods, service cold starts, outages, rate limits or revoked authorization.
- Production deployment, live migrations, invitation submissions, implementation, ticket breakdown, commits or code review as part of writing this specification.

## Further Notes

The user confirmed all seventeen design decisions and final shared understanding on October 11, 2026. One Local Master, Admin-only access, minimal metadata discovery, manual import, latest-answer ownership and exact post-commit confirmation are requirements, not optional implementation shortcuts.

Read-only investigation found existing invitation tables in the installed local database and its configured cloud-sync database, but no revision/receipt/confirmation state. It also found different database targets between development configuration and installed Cloud Sync settings. The Render invitation router responded correctly to read-only route/auth probes; its actual database correspondence, service plan and the final public invitation hostname were not established. Verify these facts before integration/rollout; do not fabricate equivalence or alter credentials automatically. Production-health success alone does not prove complete schema readiness.

Record-level mapping/provenance, credential protection and exact broad-sync exclusion/merge mechanics must satisfy this specification and be validated before use. Legacy data with unprovable correspondence is blocked for explicit repair rather than silently associated. This requirement may expose preexisting divergence; it does not authorize destructive cleanup.

Online retained responses and valid backups are the recoverable data sources. Previously confirmed records deliberately deleted online cannot be reconstructed from acknowledgements alone. Pending-response retention and deletion protections preserve offline safety; any future retention/rejection policy needs a separate decision.

The ready-for-agent label means the published specification is ready to be planned/worked against with the confirmed testing boundaries. It does not authorize this chat to automatically execute ticketing, implementation, migrations, code review or deployment.
