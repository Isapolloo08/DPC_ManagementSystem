# Online invitation synchronization: approved ticket breakdown

Parent specification: [GitHub issue #1](https://github.com/Isapolloo08/DPC_ManagementSystem/issues/1).

Status: approved and published October 11, 2026 as GitHub issues #2–#8. Implementation is recorded in [the delivery notes](../../online-invitation-sync-implementation.md). Hosted rollout remains separate.

Every ticket is a demonstrable behavior spanning its necessary persistence, API, UI and tests. Foundational work is delivered through real pairing and public submission/Cloud Sync workflows rather than separate schema-only or API-only tickets. Published tickets use ready-for-agent, reference the parent and carry the approved blocking edges. The connector lacked native sub-issue/dependency mutations, so child bodies use Part of #1 and Blocked by references. Keep the parent body/state unchanged; prefer native GitHub sub-issue and dependency relationships, with documented textual fallback when unavailable.

| Draft | Ticket | Blocked by | Deliverable |
| --- | --- | --- | --- |
| 1 | [Pair the Local Master with a verified online source](01-pair-local-master.md) | None | An authorized local Admin pairs the Local Master once through an authorized cloud Admin and sees Ready, Not paired or Reconnect required in the existing settings experience. Every LAN client uses the same receiver and pairing. This slice establishes the usable security/readiness boundary; it does not yet discover or import submissions. |
| 2 | [Retain online submission revisions and protect invitation Cloud Sync](02-retain-online-revisions.md) | 1 | A recipient submits or changes an invitation response online and it remains safely available for later manual Pull. Organizers can keep publishing invitations and using other Cloud Sync transfers without stale Push replacing online-owned answers or broad Pull importing them into the Local Master. |
| 3 | [Discover pending online submissions through the notification bell](03-discover-pending-submissions.md) | 2 | While a valid local Admin session is active, the running Local Master discovers pending submission metadata and updates event-grouped alerts. The bell opens the correct event invitation modal with pending count and connection freshness, without importing any response. |
| 4 | [Preview a pending submission and explain blocked parent mappings](04-preview-verified-submissions.md) | 3 | An Admin opens a pending submission in the event invitation modal, requests a transient preview and sees whether its existing local event/member/invitation counterparts can be verified. Missing or ambiguous correspondence is explained without creating or importing parent records. |
| 5 | [Manually Pull one submission with durable confirmation recovery](05-pull-one-submission.md) | 4 | An Admin clicks Pull for one pending submission. The latest fetched online revision is saved locally exactly once with the correct planned registration and receipt, then confirmed online. If confirmation fails, the UI says Imported locally / Confirmation pending and recovery retries confirmation without importing again. |
| 6 | [Pull Selected submissions with independent item outcomes](06-pull-selected-submissions.md) | 5 | An Admin selects pending submissions within one event and deliberately starts Pull Selected. Each item follows the safe single-Pull path and retains its own outcome; failures or interruption do not undo successful items or automatically retry failed imports. |
| 7 | [Recover manual submission synchronization after backup and restore](07-restore-synchronization-state.md) | 5 | A backup operator restores compatible Local Master data and the Admin sees the correct pending submissions again. Receiver identity, mappings, receipts and pending confirmations survive; retained online revisions missing locally require manual Pull even if already acknowledged online. |

Only direct gating edges are listed; prior dependencies are inherited. Draft 2 inherits pairing/source readiness from 1; discovery inherits both from 2. Batch Pull and backup/restore can proceed independently after single Pull. Atomic receipts, concurrency protection and durable confirmation recovery belong in the first Pull slice so no intermediate Pull implementation advertises unsafe synchronization.

Deployment facts remain explicit integration/rollout prerequisites in draft 1; feature implementation can be verified against isolated environments while real source verification is unresolved. No ticket authorizes production rollout or speculative database-target changes.
